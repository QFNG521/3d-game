# 2026-11-24

## 新项目：Aero UI（uni-app x 蒸汽模式组件库骨架）
- 背景：用户认为 uView 2.0（Gitee 仓库最后提交 2024-10-29 v2.0.38，102 个组件目录）不适用于 uni-app x 蒸汽模式，要求重构新框架。用户选择：**全新设计**（不兼容 u-* API）、**最小可跑骨架**、**全端一致**（App 三端 + Web + 微信/支付宝小程序）。
- 结论：不是改写，必须重写。uView 老代码 103 个组件用 mixin、105 个 Options API、依赖全局 `$u`、nvue 条件编译、伪元素图标；蒸汽模式只支持组合式 API、无 mixin、样式不继承、仅 class 选择器、App 端丢弃 gap/伪元素/:deep()/grid 等。
- 交付路径：`aero-ui/`，含 `uni_modules/ae-ui/`（10 个组件：button/text/icon/cell/tag/badge/divider/input/switch/popup）+ TS 设计令牌（明暗主题、品牌色可动态切换）+ `libs/style.ts` 字符串内联样式助手 + `demo/` uni-app x 工程 + `scripts/verify-constraints.mjs` 静态约束检查（已通过：12 uvue、6 ts、10 组件）。
- 架构决策：组件全部 `<script setup lang="ts">`、`defineOptions({ styleIsolation:'isolated', externalClasses:[...] })`；颜色/尺寸等由 TS token 计算成内联 CSS 字符串（避免 CSS 变量继承问题）；文字一律 `<text>`；不用 gap、伪元素、关系选择器；easycom 靠 `uni_modules/ae-ui/components/<name>/<name>.uvue` 同名目录自动扫描。
- 工具链事实：本机 HBuilderX 5.34.2026102909，CLI 位于 `/Applications/HBuilderX.app/Contents/MacOS/cli`；`cli publish`/`cli pack --precheck` 均提示"此功能需要先登录"，因此本次**未做真实编译验证**，只完成静态校验。用户若登录 HBuilderX 后可在 `aero-ui/demo` 运行/发行验证。
- 生态调研：官方 uni-ui x，社区 uView Pro X 2.0（已全面转 TS/80+ 组件）、uView Ultra、lime-UI Vapor、RiceUI、TuiPlus Vapor 已在做同类事情；自研理由是可控源码与自有设计体系。

## 真实编译反馈与修复（用户用 HBuilderX Web 端跑通）
- 坑 1：`index.html` 入口必须写 `src="/main"`，写 `/main.ts` 时 uni-app x Web 会告警并可能白屏。
- 坑 2（关键）：**`uni_modules` 必须位于 HBuilderX 项目根目录内**，否则 easycom 扫描不到，模板里的组件被编译成 `resolveComponent("ae-xxx")` 运行时查找，页面报错。已把插件从 `aero-ui/uni_modules/` 移到 `aero-ui/demo/uni_modules/ae-ui/`，页面 import 相应改为 `../../uni_modules/ae-ui/index.ts`。修复后编译产物中已出现 `__easycom_N` 的直接 import，10 个组件模块 + 全部 TS 模块均返回 200 且无编译错误。
- 调试技巧：HBuilderX 启动的 Vite dev server 可用 `curl 'http://localhost:5173/pages/index/index.uvue?import'` 查看转换后的模块；搜索 `resolveComponent("ae-` 表示 easycom 未生效，搜索 `__easycom_` 表示生效。逐个 `curl .../components/<name>/<name>.uvue?import` 可定位单组件编译错误。

## Aero UI v2 重写（2026-11-25，参考 uView Pro X）
- 用户否定第一版"实在不太好"，要求参考 uView Pro X（`uview-pro-x` DCloud 插件，2.0.10、80+ 组件、TS+UVUE、付费源码版 99 元、今日仍更新）重做，但**不需要完整复刻**。
- 第一版根因：架构层次太浅——无插件入口、主题靠 JS 逐组件算内联样式、无 v-model/slot、组件 API 无分层、无 hooks/类型/文档。
- 新版交付 `aero-ui-v2/`（旧版保留对比）：19 组件（新增 config-provider/loading/checkbox(+group)/radio(+group)/cell-group/empty/toast），核心改进：
  1. **CSS 变量主题**：`--ae-*` 令牌 + `ae-config-provider` 根节点注入，`useTheme()` 运行时切主题/明暗并持久化，组件样式用 `var(--ae-x, 回退值)`，不再逐组件算样式。
  2. **`app.use(AeroUI, { theme })` 插件入口**（命名导出 + default）。
  3. **v-model**：input/switch/checkbox/radio 用 `modelValue` + `update:modelValue`；checkbox-group/radio-group 用 provide/inject 协作。
  4. 分层 API：type/size/shape/plain/disabled/loading/customClass/customStyle；slot（button/cell/input prefix/popup/toast）。
  5. $ae 全局属性 + libs/utils（addUnit/createStyle/toStyle/cls/hexToRgba/debounce/throttle）+ 统一 types.ts。
- **关键兼容性决策**：uni-app x 编译器未确认支持类型化 `defineEmits<{...}>()` 与 `inject<T>()`，已全部改为数组式 `defineEmits(['x'])` 与 `inject('k') as T`（第一版验证过数组式可编译）。props 一律 camelCase（kebab-case 泛型 defineProps 会出问题）。
- 验证：`npm run verify` 包含两层——(a) 约束扫描（禁 :root/伪元素/gap/:deep/grid/mixin/选项式/旧条件编译、组件 defineOptions+isolated、easycom 规则、vapor 配置）；(b) **用 HBuilderX 内置 `@vue/compiler-sfc` 对 21 个 .uvue 做 parse+compileScript+compileTemplate（全通过）**。脚本路径 `scripts/verify-syntax.mjs`，createRequire 指向 HBuilderX 内置 cli 的 package.json。
- CLI 真实编译仍受阻：`cli publish` 需登录；直接用内置 vite 拼工程会因 HBuilderX 内置 uni-app 蒸汽版依赖定制 Vue（`injectHook`）与普通 vue 不匹配而失败——属工具链拼装问题，非代码问题。**真机/HBuilderX GUI 运行验证仍需用户完成**。
- uView Pro X 设计要点（参考）：主题令牌→CSS 变量（page 选择器承载）、external-class 定制、分层组件 API、零三方运行时依赖、Agent Skills（pnpx skills add uview-pro/skills）。
